# 合规智能交付 Agent（CyberLobster）

数据分析与数据出仓场景里，规范往往写在文档里，执行却靠人和经验。把任务交给大模型之后，新的风险又出现了：模型可以说「已经脱敏」，文件里却仍是明文；或者用表格预览里的显示格式做自检，把本来不合格的结果当成通过。

本项目是一个运行在本地的 **合规智能交付 Agent**：用户用自然语言下达分析 / 出仓任务，系统在沙箱中生成并执行处理代码，按本地知识库中的规范组织交付；关键产物在出门前再经过**程序级硬校验**——能否交付，不由模型口头保证，而由确定性规则裁定。

当前主要覆盖两个方向：

1. **规范驱动的数据分析交付** — 检索本地政策与规范，在受控环境中完成清洗、统计、导出等处理  
2. **出仓前的合规验收闭环** — 交付物显式声明所依据的规范，并由框架自动对账、硬验；失败则反馈并有限次返工  

### 项目定位（便于快速判断）

| 本项目是 | 本项目目前不是 |
|----------|----------------|
| 本地可运行的数据分析 / 出仓助手 | 通用代码审查或安全扫描平台 |
| 「检索规范 → 执行 → 程序验收」的工程闭环 | 只靠 Prompt 约束的 Demo |
| 以本地知识库为 Policy 来源 | 联网搜索型知识助手 |
| 可复现的校验层评测与冒烟 | 宣称端到端替代人工合规审批的黑盒系统 |

## 为什么做

出仓与脱敏一类工作，传统路径依赖人工反复对照规范，成本高、口径也不稳定。若把流程直接交给大模型「写代码并交付」，常见失败模式包括：

- **口头合规**：对话里声称已处理，落盘文件未达标  
- **假自检**：用易产生展示误差的检查方式通过自检（例如小数位在预览中被吞掉）  
- **瞒报交付**：产生了文件却不声明，或拿旧文件误触发验收  

因此本项目的目标可以概括为：

> **降低人工验收成本，提高交付可信度。**  
> Agent 负责理解任务与生成处理逻辑；规范来自本地 RAG；**最终是否允许交付，由程序规则说了算。**

能力叙事可以记成一条链路：

**理解任务 → 检索规范并打上 Policy Context → 沙箱执行落盘 → 交付清单声明归属 → 硬校验 / 失败回灌。**

## 怎么做（工程要点）

### 大模型负责「办事」，框架负责「放行」

系统把职责拆开：LLM 做意图理解、步骤规划与代码生成；RAG 提供组织内部的规范文本；沙箱限制执行面；Job 结束后的 `spec_validator` 对声明过的交付单元做字段与文件级检查。校验失败会把错误回灌给 Agent，在有限次数内返工，而不是无限循环。

### 规范可追溯：RAG → Policy Context → 交付单元

用户勾选知识库后发起任务；检索成功时，程序写入本轮候选 Policy Context（如 `ctx_1`）。Agent 在交付清单中用 `policy_refs` 声明「这些文件依据哪些 ctx」。框架核对引用是否真实，再决定仅登记还是进入硬验。

同轮可以同时存在「草稿仅登记」与「出仓必须硬验」——归属按交付单元拆分，而不是整次任务一刀切。

### 三层防线，而不是单点提示词

1. **Checklist**：业务代码生成前，先把检索到的关键规矩写入可检查的清单意识  
2. **产物自检**：脚本写完后读回核对，减少「写完不验」  
3. **框架硬校验**：整轮任务结束后由程序扫描；不达标则拦截并回灌  

出仓规则示例包括：必要文件是否齐全、手机号掩码形态、分数在 **CSV 原文**上是否满足小数位要求、审计文件行数是否一致等。用文件原文验收，是为了避开展示层造成的假通过。

### 堵瞒报与可回滚执行

本轮若产生了新文件却没有交付清单，将直接判定为 `MISSING_MANIFEST`。结合写时备份（COW），系统能够识别本轮新建文件，并在中断时回滚工作区改动。沙箱优先采用 Docker（工作目录隔离、禁网、超时终止），也可回退到本机受控子进程。

### 知识库工程化

采用 ParentDocument 检索：小块负责召回精度，命中后再取完整父块补足上下文。正文检索要求用户硬勾选知识范围，避免模型自行串库。示例语料包含出仓脱敏（`engineering`）与学术文档类（`academic`）等。

## 已实现能力

| 能力 | 作用 |
|------|------|
| 本地对话式交付 | Dash 界面勾选知识库、下达中文任务、查看产物路径 |
| 规范检索 | 知识库目录浏览 + 向量检索；检索成功写入 Policy Context |
| 沙箱执行 | pandas / numpy / matplotlib / plotly 等常见分析栈；支持 Docker / 本机后端 |
| 合规验收 | 交付清单、归属对账、硬校验、有限次回灌 |
| 会话治理 | Tool 轨迹清洗、弹性上下文窗口、会话归档与过期任务防脏写 |
| 评测与冒烟 | 可复现的校验层对比实验与主路径冒烟脚本 |

在合成出仓缺陷样本上的校验层对比（详见 [`evals/EVAL_REPORT.md`](./evals/EVAL_REPORT.md)）：以「文件存在 + pandas 软检查」为基线时，缺陷检出约 **16%**；现行程序硬校验约 **100%**。该数字衡量的是**校验层增益**，不是大模型端到端准确率。

## 正在拓展的方向

当前版本已经形成可用的本地交付闭环，并把「信任」从模型自觉转移到可执行的验收机制上。后续拓展主要沿着三条线推进：

### 1. 更完整的规范覆盖与更聪明的归属审计

现有硬校验优先夯实出仓脱敏等主路径底线。下一步会扩大规则覆盖（更多字段与文件形态），并增强对「用了规范却未正确声明归属」一类漏绑问题的识别能力，让 Policy 追溯从「假引用可拦」进一步走向「漏声明也可审计」。

### 2. 更强的可观测性与评测门禁

把关键验收、回灌与沙箱事件沉淀为更清晰的运行轨迹，便于定位「哪一步放过了不合格产物」。同时把现有 evals / smokes 更紧地接到日常迭代中，使规范或校验逻辑变更时，能够快速看到回归结果。

### 3. 更易扩展的 Policy 包与执行后端

让不同业务线能够以更低成本挂入自己的知识库与规则包，而不是改动机架核心；并持续强化 Docker 路径下的隔离体验与配置友好度。目标是：换一套规范、仍走同一条「检索 → 执行 → 验收」叙事。

> 以上为进行中的演进，不等同于当前仓库已全部交付。现网能力以「已实现能力」为准。

## 快速开始

环境：Python 3.11+，以及可用的大模型 API Key。

```bash
cd cyber_lobster_project
cp .env.example .env          # 填写 DEEPSEEK_API_KEY
python build_knowledge.py     # 首次或 knowledge_docs 变更后需重建索引
python app.py
```

沙箱配置见 `docker/README.md`（`SANDBOX_BACKEND=auto|docker|local`）。界面地址以终端输出为准。

建议自检：

```bash
python smokes/run_all.py
python evals/_eval_before_after.py    # 更新/复核 EVAL_REPORT.md
python evals/_eval_rag_suite.py       # 需已完成建库
```

## 使用与安全约定

请勿将真实 API Key 提交到版本库。知识库与出仓样例仅供演示与工程验证；在真实业务数据上使用前，请替换为组织自有规范，并确认沙箱与权限策略符合内控要求。`chroma_db/`、会话归档与大部分 `workspace/` 产物属于本地运行时文件，默认已由 `.gitignore` 排除。
